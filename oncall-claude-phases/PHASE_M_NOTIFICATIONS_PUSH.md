# PHASE M — NOTIFICATIONS, PUSH NOTIFICATIONS, AND DELIVERY INFRASTRUCTURE

Implement a new phase for the **Oncall Philippines** project.

Work inside the existing `oncall` project.

All Phases **A–L** are already implemented and must be treated as the current source of truth.

Do not redesign or weaken the authorization, mobile/web role boundaries, verification, enforcement, cashout, SMS/OTP, or audit architecture established in previous phases.

Complete **Phase M only**.

Do not begin Phase N.

---

# OBJECTIVE

Implement production-ready notification infrastructure for Oncall Philippines.

The system must support:

- Laravel database/in-app notifications
- Flutter push notifications
- Firebase Cloud Messaging (FCM)
- Android and iOS device registration
- multiple devices per user
- notification preferences
- event-driven notification dispatch
- notification history
- read/unread state
- deep-link/navigation targets
- delivery logging
- retries and failure handling
- device token lifecycle management
- duplicate-notification prevention
- admin-managed notification templates/settings
- optional SMS fallback for selected critical notifications
- strong protection against sensitive-data leakage

Laravel remains the authoritative source of truth.

Flutter must never decide whether a business event is valid.

Flutter only receives and displays notifications generated by the Laravel backend.

# STEP 12 — QUEUED DELIVERY

Conceptually:

```text

    ↓
```

Use appropriate `afterCommit()` behavior or equivalent so notifications are not dispatched before the underlying database transaction successfully commits.
